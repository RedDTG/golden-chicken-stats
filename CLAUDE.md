# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A single-file Discord bot (`bot.py`) that watches one channel for UnbelievaBoat "cockfight" result embeds and logs each fight to a Google Sheet via the Sheets API. Real-time logging writes to a local SQLite file first (the source of truth) and a background task syncs it to Sheets by batch — see "SQLite as source of truth" below for why.

## Setup & running

```bash
pip install -r requirements.txt
cp .env.example .env   # then fill in the values
python bot.py
```

Required environment variables (see `.env.example`, loaded via `python-dotenv`):
- `DISCORD_BOT_TOKEN` — bot token from the Discord Developer Portal.
- `WATCH_CHANNEL_ID` (optional) — if set, the only channel the bot listens to; if empty/unset, the bot listens across every channel it can see.
- `UNBELIEVABOAT_ID` (optional) — if set, only embeds authored by this bot ID are parsed; otherwise any bot message in the channel is considered.
- `GOOGLE_CREDENTIALS_FILE` (default `credentials.json`) — Google service-account key file, not committed (gitignored).
- `GOOGLE_CREDENTIALS_JSON` (optional) — the service-account key as a raw JSON string, used instead of `GOOGLE_CREDENTIALS_FILE` when set (takes priority). Useful in deployments (e.g. Coolify) where providing a file is inconvenient.
- `GOOGLE_SHEET_ID` — target spreadsheet ID (from its URL).
- `GOOGLE_SHEET_TAB` (default `Cockfights`) — worksheet/tab name; must already exist in the sheet.
- `OVERVIEW_SHEET_TAB` (default `Overview`) — second worksheet/tab name for the per-player rollup kept up to date by `_update_overview_impl()`; must already exist in the sheet.
- `TIMEZONE` (default `Europe/Paris`) — IANA zone name used to render the Horodatage column, via `zoneinfo`. Deliberately independent of the host machine's system timezone (a bare `.astimezone()` on a UTC-configured server/container silently produces `+00:00` timestamps instead of local time — this bit us once, see `tzdata` in `requirements.txt` for the portable data source).
- `BANK_SHEET_TAB` (default `Bank`) — third worksheet/tab name for the `+bal` tracking described below; must already exist in the sheet.
- `TRACKED_MEMBER_IDS` (optional) — comma-separated Discord user IDs whose `+bal` results get logged to the `Bank` tab. Empty/unset disables the feature entirely (no fetch at startup, no matching at runtime).
- `DB_PATH` (default `bot.db`) — path to the local SQLite file that is the source of truth for Stats/Bank. **Must be on a persistent volume in containerized deployments** (see "SQLite as source of truth" below) — the `Dockerfile` doesn't declare one.
- `SYNC_INTERVAL` (default `15`) — seconds between two SQLite → Sheets sync passes (Stats, Bank, Overview all flushed together).
- `RECORD_CHANNEL_ID` (optional) — channel to `@everyone`-ping in when a `Victoire` beats the highest win-probability ever recorded for that server. Empty/unset disables the feature.
- `BACKFILL_SHEET_TAB` (default `Backfill`) — worksheet `run_backfill()` writes its live progress to; must already exist in the sheet.
- `BACKFILL_HEARTBEAT_INTERVAL` (default `30`) — minimum seconds between two progress writes to `BACKFILL_SHEET_TAB`, deliberately coarser than `BACKFILL_PROGRESS_INTERVAL` (which only logs) to avoid piling up Sheets writes over a run that can take hours.

There is no test suite, linter, or build step in this repo currently.

## SQLite as source of truth

Real-time logging used to write straight to Google Sheets on every event (`_sheet.append_row(...)` per fight, `_bank_sheet.append_row(...)` per `+bal`), with no error handling. That's fragile in two ways this repo actually hit: the Sheets API has a per-100-seconds quota, and every write was a synchronous network call with no retry — a quota hit or network hiccup silently dropped that row forever, and nothing upstream ever caught the exception to even log it. This got noticed as "some `+cf` results seem to go missing" and, separately, as `update_overview()` freezing (see below) — both symptoms of the same root cause.

Fix: SQLite (`init_db()`, module-level `_db` connection to `DB_PATH`, `PRAGMA journal_mode=WAL`) is now the source of truth. `on_message` only ever writes to SQLite (`INSERT OR IGNORE INTO stats/bank ... synced=0`) — a local disk write, no network, effectively never fails. A background `@tasks.loop(seconds=SYNC_INTERVAL)` (`sync_loop`, started in `on_ready`) calls `sync_to_sheets()`, which pushes whatever's `synced=0` to Sheets in batched calls (`append_rows`/`batch_update` instead of one call per row) and then recomputes `Overview`. Because the bot runs single-threaded on one asyncio event loop, sharing one `sqlite3.Connection` across `on_message`/the sync loop/`run_backfill()` without `check_same_thread=False` is safe.

Each of the three steps in `sync_to_sheets()` (`_flush_stats()`, `_flush_bank()`, `_update_overview_impl()`) is wrapped in its own `try`/`except gspread.exceptions.APIError`, logged rather than raised. Nothing is ever lost this way: a row stays `synced=0` until a sync attempt actually succeeds, so a failure just delays it to the next tick instead of dropping it. This is the same "let it be delayed, never silently lost" principle `update_overview()`'s earlier debounce fix used, just applied one layer lower (before rows even reach the point where a fight could be forgotten, not just before Overview's aggregate goes stale).

**Bootstrap** (`_bootstrap_from_sheets()`, called once from `init_db()` at import time): if the `stats`/`bank` tables are empty — a fresh `DB_PATH` file, e.g. after a first deploy or a volume that wasn't there before — the current content of the `Stats`/`Bank` sheets is imported in one `get_all_values()` call each, marked `synced=1` (already on Sheets, nothing to push). `INSERT OR IGNORE` on `message_id` (primary key) means any duplicate `Message ID` already sitting in the live sheet (this repo had ~800 of them by the time this was built) gets silently deduplicated rather than imported twice. Without this bootstrap, a fresh SQLite file would have no memory of the sheet's existing history, and `Overview`/`last_win_strength()`/`/stats` (all SQLite-sourced now, see below) would look like the player base had zero history.

**Deployment caveat, worth repeating**: the `Dockerfile` declares no volume. On a platform like Coolify, a redeploy typically recreates the container from scratch, wiping any file not on a mounted volume — including `DB_PATH`. Bootstrap means a wipe isn't a *data-loss* disaster (the sheet's own history gets reimported), but any row logged locally and not yet synced at the moment of the wipe is gone. `DB_PATH` should point at a volume that survives redeploys for the durability guarantee to mean anything beyond "survives a plain crash/restart".

**Correcting rows without duplicating them** (`_flush_stats()`): a plain "append everything unsynced" would work for brand-new rows, but `/backfill` corrections re-mark an *already-synced* row `synced=0` to push a fix — appending again would duplicate it in the sheet instead of correcting it in place. The `stats` table has a `sheet_row` column (nullable) recording which Sheets row a given `message_id` lives at once it's first appended. `_flush_stats()` splits unsynced rows into `sheet_row IS NOT NULL` (known position → `batch_update` a `A{row}:H{row}` range, exactly the old row-tracking `_existing_rows()` used to do, just persisted locally instead of re-derived from a live scan each time) and `sheet_row IS NULL` (brand new → `append_rows`, then `sheet_row` is back-filled from the response's `updates.updatedRange` via `_first_appended_row()`/`APPEND_ROW_RE`, since `append_rows` places N rows in one contiguous block starting at a known row). `bank` has no such column: Bank is real-time-only, never corrected, so every unsynced row is always a plain append.

**Reads moved to SQLite too**: `last_win_strength()`, `_update_overview_impl()`'s aggregation, and `build_stats_embed()` (used by `/stats`) all query `_db` instead of calling `_sheet.get_all_values()`. This isn't just about symmetry — it's what actually fixed `update_overview()`'s freeze at the root instead of papering over it with a debounce: the expensive full-sheet Sheets read that was burning the quota is gone entirely, replaced by a local SQL query. It also means these reads see rows the instant they're logged, before the next sync tick even runs (SQLite is always at least as fresh as Sheets, usually fresher).

## Record announcements

`_maybe_announce_record()` pings `@everyone` in `RECORD_CHANNEL_ID` whenever a real-time `Victoire` beats the highest win-probability ever recorded *for that server* (rows are scoped by the Serveur column, same convention as `/stats`). State is `_best_strength_by_server: dict[str, int]`, loaded once at startup by `_load_best_strength()` (a single grouped `MAX(CAST(strength AS INTEGER)) ... GROUP BY server` query over the SQLite `stats` table — `CAST` matters, `strength` is stored as text and a plain `MAX` would sort `"9"` above `"62"` lexicographically) and refreshed the same way, silently, after a `/backfill` that changed anything (backfill only ever *discovers* history that already happened; treating that as a new "record" and pinging the channel over it would be nonsensical and spammy, so that path updates the tracked max without calling the announce function at all).

Only called from `on_message`'s real-time path, after the row is already committed to SQLite — a message-link build failure or a `discord.HTTPException` sending the announcement (caught, logged) never risks the fight itself going unlogged, since by that point it's already durable. The message link is built directly (`https://discord.com/channels/{guild.id}/{channel.id}/{message.id}`) since discord.py has no jump-link helper; the function bails out early if `message.guild` is ever `None` (shouldn't happen given this bot only processes guild channels, but a link isn't constructible without it). The bot needs the "Mention @everyone" permission in `RECORD_CHANNEL_ID` for the ping to actually notify — `channel.send(content="@everyone", ...)` only pings if that literal token is Discord-recognized as a mention, which requires the permission and default (non-restrictive) `allowed_mentions`.

## Architecture

1. **Startup**: env vars are read, a `gspread` client is authorized against `GOOGLE_SHEET_ID`/`GOOGLE_SHEET_TAB`, `init_db()` creates the SQLite tables and bootstraps them from Sheets if empty (module level, before the bot connects to Discord). `on_ready` calls `ensure_header()` to (re)write the header row (`HEADER`) if it doesn't already match, and starts `sync_loop` (guarded by `is_running()`, since `on_ready` can fire again on reconnect).
2. **Message filtering** (`on_message`): messages are discarded unless they're in `WATCH_CHANNEL_ID` (when set — otherwise any channel is accepted), from a bot account (optionally matching `UNBELIEVABOAT_ID`), and contain embeds.
3. **Parsing** (`parse_cockfight_embed`): text-matches the embed description for `"lost the fight"` / `"won the fight"` (case-insensitive), pulling the player name from `embed.author.name` (stripped of a trailing `#1234` legacy discriminator via `DISCRIMINATOR_RE`, so old and current rows for the same player use the same pseudo), the payout from the `WIN_GAIN_RE` regex on a win (matched against the digits immediately preceding "richer", since UnbelievaBoat's custom currency emoji embeds a numeric snowflake ID between "made you" and the amount), and the win-probability percentage from `embed.footer.text` via `PERCENT_RE` (not the description, and not a regular embed field). A defeat also matches on `"chicken died"` — UnbelievaBoat's ~2019 embed format (`embed.author.name` = `"Pseudo#1234"`, description = `"Your chicken died"`, no probability footer, no fields), superseded since by `"lost the fight"` but still present in old channel history a `/backfill` needs to be able to re-read. Returns `None` when the embed isn't a recognized cockfight result.
4. **Bet lookup and player ID on every result**: neither win nor loss embeds carry a Discord ID (only `embed.author.name`, UnbelievaBoat's display pseudo, which isn't guaranteed unique on a server — nickname/username collisions happen), so `find_command_info()` walks the channel history backwards (up to 10 messages before the result) looking for the player's own `+cf <amount>` command message (matched via `BET_RE`, and matched to the player by comparing `embed.author.name` against both the message author's username and display name, since UnbelievaBoat's embed author name doesn't necessarily match `Member.display_name`). It returns both the bet amount (used only on a `"Defaite"`, where `gain` is set to the negative bet amount, e.g. `-100`) and `prev.author.id`, stored in the `ID Joueur` column — the stable key `_update_overview_impl()` groups by. Known limit: the search still filters candidates by pseudo text, so two identically-named players betting in quick succession could have the wrong one's ID attributed — unavoidable without a true request/response link from UnbelievaBoat itself.
5. **Probability estimate on a loss**: the loss embed also never states a win-probability (no footer at all), so `last_win_strength()` (bot.py, SQLite-backed) / the in-memory `last_win_percent` map (`run_backfill()`) looks up that player's most recent logged `"Victoire"` row and uses its Probabilite + 1 as an estimate for the loss row, or `50` if the player has no prior win on record (including their very first logged result being a loss). This is a deliberate approximation, not a value read from Discord. `last_win_strength()` picks the row with the latest Horodatage via `ORDER BY timestamp DESC LIMIT 1` (safe as a plain string sort because every row's Horodatage carries the same fixed-offset `TIMEZONE` suffix) — `run_backfill()` can add older, thread-sourced rows after newer ones already logged, so row/insertion order alone isn't chronological. Still matches by pseudo (`WHERE player = ?`), so it shares the same duplicate-pseudo blind spot as the bet lookup above — not ID-based, unlike Overview.
6. **Local write, then batched Sheets sync**: each parsed result is `INSERT OR IGNORE`d into the SQLite `stats` table (`synced=0`) — see "SQLite as source of truth" above for why this replaced a direct `_sheet.append_row(...)` call, and for how the periodic sync afterwards gets it onto the `Cockfights` sheet without duplicating corrections. `timestamp` is `message.created_at.astimezone(TIMEZONE)` — the message's own creation time, same source `run_backfill()` uses, so a real-time log and a later backfill of the same message always produce the same Horodatage. (An earlier version used `datetime.now(TIMEZONE)`, the moment the bot processed the message, but on a busy channel that measurably lags behind send time — bit us once, see the ~4min drift on a `Defaite` row.) The Serveur and ID Joueur columns were added at the end of `HEADER` (not inserted between existing columns) specifically to avoid shifting the columns of rows already present in a live sheet.

Because parsing is purely regex/string-matching against UnbelievaBoat's embed text (and the player's own bet command), any wording change in that bot's cockfight messages requires updating `WIN_GAIN_RE`, `PERCENT_RE`, `BET_RE`, or the `"lost the fight"`/`"won the fight"` checks in `parse_cockfight_embed`.

## Bank tracking (`+bal`)

Passive-only: the bot never sends `+bal` itself, it just logs whenever a `+bal` result for a tracked member happens to appear in the watched channel (triggered by anyone — the tracked member themselves, another user, or another bot/self-bot). Lives in the same `on_message`-adjacent embed loop as cockfight parsing, but **not** wired into `run_backfill()` — Bank logging is real-time only, there is no historical rescan for it (its SQLite bootstrap still imports whatever's already on the `Bank` sheet at first run, though — see above).

1. **Resolving IDs to names** (`on_ready`): `TRACKED_MEMBER_IDS` is a set of Discord snowflakes, but UnbelievaBoat's `+bal` embed doesn't expose the target's ID anywhere — only `embed.author.name`, the same raw-username field already relied on as `Joueur` for cockfights (see `parse_cockfight_embed` above). So at startup each ID is resolved once via `bot.fetch_user()` into its lowercased username, cached in the module-global `tracked_usernames`. A user who renames after the bot started keeps being matched under their old username until the bot restarts. If `TRACKED_MEMBER_IDS` is empty, `tracked_usernames` stays empty and `on_message` skips the balance-parsing branch entirely (cheap no-op check on every embed).
2. **Parsing** (`parse_balance_embed`): rejects the embed outright unless `embed.author.name.lower()` is in `tracked_usernames` — this is what keeps the Bank tab scoped to only the configured members even though the bot sees every `+bal` in the channel, not just theirs. Field values go through the same `CUSTOM_EMOJI_RE` strip as `golden-chicken-finder`'s balance parsing before the digits are extracted (`AMOUNT_RE`) — UnbelievaBoat's custom currency emoji embeds a numeric snowflake between the amount and the field text, and matching digits before stripping it grabs the emoji's ID instead of the balance (this exact bug already happened once in the sibling repo, see its CLAUDE.md). Matches `Cash`/`Bank`/`Total` fields by prefix (case-insensitive on `field.name`), same convention as the win-percent/gain parsing elsewhere in this file. Returns `None` (nothing logged) if no `Total` field was found, since that means the embed isn't really a balance response.
3. **Local write, then sync**: one row per observed `+bal` — `INSERT OR IGNORE INTO bank (...) synced=0` — pushed to the `Bank` sheet by the same `sync_to_sheets()`/`_flush_bank()` pass as everything else, mirroring `stats` but with its own header (`BANK_HEADER`) and tab (`BANK_SHEET_TAB`). No overview/rollup sheet for Bank — it's a raw log, not aggregated.

Known gap: because matching is by username rather than ID, `parse_balance_embed` would also (mis)match an *untracked* user who happens to share a username with a tracked one — accepted as unlikely given Discord's globally-unique username constraint, same trust level the codebase already extends to `embed.author.name` elsewhere.

## Backfill

The rescan logic itself (`run_backfill()`) lives in `bot.py` so it can be reused from two entry points:

- **`backfill.py`**: a thin one-off script (run manually with `python backfill.py`) that opens its own `discord.Client`, calls `run_backfill(client)` once in `on_ready`, then disconnects. Importing `bot` runs `init_db()` at module level as a side effect, same as the main bot.
- **`/backfill` slash command** (`bot.py`): the same rescan triggered from within the already-running bot, as an `app_commands` command registered on `bot.tree` (synced in `on_ready`), gated by `@app_commands.checks.has_permissions(administrator=True)` and an `asyncio.Lock` that rejects a second concurrent run. Since a backfill can run well past Discord's 3-second interaction deadline, it immediately `defer()`s and reports the corrected/added row counts via `followup.send()`. Works in any channel/guild the bot is in, independent of `WATCH_CHANNEL_ID`. The bot's Discord invite link must include the `applications.commands` OAuth2 scope (in addition to `bot`) for slash commands to register at all.

Commands are synced **per-guild only** (`_sync_guild_commands()`: `copy_global_to()` + `sync(guild=...)`), called for every guild in `on_ready` and again in `on_guild_join` for guilds joined later. A global-only sync (`tree.sync()` with no `guild=`) can take up to an hour to show up on Discord clients after adding/changing a command, but combining a global sync *and* per-guild syncs registers each command twice — Discord then shows two separate entries with the same name in the picker, since a global command and a guild-scoped command with identical names are distinct registrations, not automatically deduplicated. `on_ready` also does a one-off `bot.http.bulk_upsert_global_commands(bot.application_id, [])` (bypassing `tree.sync()`, which would also wipe the tree's own global command list that `copy_global_to()` reads from) to clear out any global commands left over from an earlier deploy. Sync failures are logged instead of failing silently.

Either way, `run_backfill()` rescans each watched channel plus all of its threads (active, archived, public and private, via `_channel_group()` — `channel.history()` alone doesn't descend into threads), merges and sorts every message by ID (chronological) before processing, and upserts every parsed result into the SQLite `stats` table (`INSERT ... ON CONFLICT(message_id) DO UPDATE SET ... synced=0`) rather than writing to Sheets directly — corrected/added counts are computed from a `message_id` snapshot taken before the scan starts (`existing_ids`), not from the upsert itself. The `ON CONFLICT` clause deliberately never touches `sheet_row`, so a correction keeps whatever row it already had on Sheets (routed to an in-place `batch_update` by `_flush_stats()`) while a brand-new row starts with `sheet_row = NULL` (routed to `append_rows`) — see "SQLite as source of truth" above. Once the scan finishes, `run_backfill()` calls `sync_to_sheets()` directly (bypassing `sync_loop`'s interval) so an admin running `/backfill` sees the result on Sheets immediately rather than waiting up to `SYNC_INTERVAL` seconds. Horodatage is recomputed from `message.created_at.astimezone(TIMEZONE)` — the message's real creation time — so re-running the backfill also retroactively fixes any row written under a wrong/inconsistent timezone. Useful after a parsing bug fix or after the bot was offline for a while (or after a fresh/wiped `DB_PATH` needs its `ID Joueur`/`sheet_row` bookkeeping rebuilt beyond what the plain Sheets bootstrap captured). It needs the "Read Message History" permission on the watched channel(s). Because it processes history in chronological order, it rebuilds the "last win % per player" state as it goes rather than querying SQLite/the sheet (rows aren't committed until each message is upserted, but downstream stats consumers won't see backfill's corrections until `sync_to_sheets()` runs at the very end).

**Progress visibility** (`_update_backfill_status()`): a full backfill over a large channel history (tens of thousands of messages, each cockfight result triggering up to 10 more `history()` calls via `find_command_info`) can run for hours with nothing else observable in the meantime — there's no resumability, and the only other feedback is the process's own logs. `_update_backfill_status()` writes a single status row (`Statut`, `Salon`, `Dernier message traite`, `Corrigees`, `Ajoutees`, `Derniere mise a jour`) to `BACKFILL_SHEET_TAB!A2:F2`, called at the start (`"En cours (recuperation)"`), throttled to at most once per `BACKFILL_HEARTBEAT_INTERVAL` during both the history-gathering and the processing loops, and at the end (`"Termine"` with final counts, or `"Erreur (...)"` with the counts accumulated so far — the `try/except Exception: ... raise` around the main loop guarantees this write happens even on an unexpected failure, while still propagating the exception so `/backfill`'s own error handling and Discord reply are unaffected). This makes progress checkable via the Sheets API alone, without needing access to the bot's process logs.

## Stats

`/stats` (open to anyone, no permission gate) builds a Discord embed from `build_stats_embed()`, which queries the SQLite `stats` table filtered to the invoking `interaction.guild.name` (matching the Serveur column — stats are per-server even though one sheet/database can hold rows from several guilds), then reports combat/win/loss counts, the player with the best and the player with the worst winrate (wins / total games played, via `collections.Counter`; not raw win/loss counts, since those trivially favor whoever has played the most), and the win with the single highest Probabilite value (and who scored it).

## Audit

`/audit` (open to anyone, no permission gate) builds an embed from `build_audit_embed()` reporting SQLite's own state for the invoking server — deliberately queried straight from `_db`, not by reading the Sheets mirror, since Sheets can lag behind or (if a sync ever silently failed) diverge from what SQLite actually holds. Reports: total logged combats, how many are missing `player_id` (count + %, plus a top-5 breakdown by player — this is what first surfaced that `/backfill` hadn't meaningfully resolved historical IDs despite being recommended after the ID-grouping feature shipped, since long-inactive players sat at 92–100% missing), how many `stats`/`bank` rows are still `synced = 0` (i.e., known to SQLite but not yet pushed to Sheets — a nonzero count here just means "wait for the next `sync_loop` tick", not data loss), and the earliest/latest Horodatage covered. It's a read-only diagnostic, safe to run anytime.

## Overview sheet

`_update_overview_impl()` keeps a second worksheet (`OVERVIEW_SHEET_TAB`, one row per player plus a `"Total"` aggregate row, columns `Total / Defaites / Victoires / Winrate / Meilleur poulet / Rentabilite / ID Joueur`) in sync with SQLite: it re-derives per-player and global totals from every row in the `stats` table on each call (games played, defeats, wins, Winrate = wins / games played as a rounded percentage divided by 100 so the cell holds a 0–1 fraction Sheets can format as `%`, Meilleur poulet = the highest Probabilite among that player's wins likewise divided by 100, and Rentabilite = the sum of the Gain column with non-numeric/blank gains counting as 0).

Grouping key is `player_id` from SQLite, not the Joueur pseudo — added specifically because a server can have two different members sharing the same displayed pseudo/nickname, which used to silently merge their stats into one Overview row. Rows logged before `player_id` existed carry an empty string; those fall back to grouping by lowercased pseudo text (`f"name:{player.lower()}"` internally, vs. `f"id:{player_id}"` when known) until a `/backfill` run retroactively resolves and stamps their ID. Matching an aggregated key to an existing Overview row tries `existing_by_id` first (column H on the Overview sheet), and only falls back to exact string equality on column A (the pre-ID convention) when no ID is known yet for that key — with a `claimed_name_rows` guard so that if two distinct IDs both fall back to the *same* legacy same-pseudo row, only the first claims it and the second gets a brand-new row instead of the two silently overwriting each other on alternating calls. Reordering these columns only requires changing `OVERVIEW_HEADER` and the `values` list in tandem (both by position, no explicit column letters tie them together) — existing rows get overwritten in the new order on the next call rather than needing an actual spreadsheet column insert. Unlike `/stats`, this aggregates across every server in the sheet/database (the Overview layout has no Serveur split; `/stats` itself still reports by pseudo, not ID).

`_update_overview_impl()` is called as the last step of `sync_to_sheets()` — every `SYNC_INTERVAL` seconds via `sync_loop`, and once more immediately at the end of `run_backfill()`. It used to be triggered after every single real-time log and read the entire live Stats sheet on each call, which is what caused the quota-driven freeze this whole SQLite migration was built to fix in the first place (see "SQLite as source of truth"); now its read side is a local SQL query over the same table `on_message` just wrote to, so the expensive/quota-risking part is gone regardless of how often it's called — the `SYNC_INTERVAL` cadence exists to batch the *write* to Sheets, not to protect a read.
